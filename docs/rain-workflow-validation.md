## 单个 BPM 锚点的原因

截图项目来自已生成曲包，导入的 MC 只有 **0 ms / 144 BPM**。第三步原来的「分析节奏活动」生成全曲的段落活动计划，并没有重新生成或写入 BPM 锚点。RoFormer 分离保留原曲时钟，也不会修改节拍参考。

对截图项目的完整原曲做独立 CPU 分析：

| 证据 | 实测结果 | 解释 |
|---|---|---|
| 原曲长度 | 230.080 秒 | 分析覆盖全曲，没有只分析 12 秒 |
| 全局拍速估计 | 143.555 BPM | 与导入的 144 BPM 接近 |
| 局部一倍拍速候选 | 约 143.18–144.91 BPM | 离散分析分辨率与跟拍误差不等于真实变速 |
| 半倍、双倍候选 | 约 72 / 286–289 BPM | 支持度相近，不能据此新增变速锚点 |
| 16 秒窗口 | 全部保留未确认状态 | 没有足够证据自动确认新的 BPM 变化 |
| 节奏活动 | 疏密显著变化，尾部降至静音 | 即使只有一个 BPM 参考，仍能逐段适配模型条件 |

这不能证明歌曲绝对恒速；它说明本次证据不足以把倍速歧义当作真实 BPM 变化。完整证据保存在本地 `work/rain-original-tempo-evidence.json`。

第三步现在分开展示**当前使用的锚点**和**原曲逐段拍速候选**，包含原曲范围、活动疏密、当前组合模型条件、预算调整、半/双倍速歧义及原曲试听入口。分析显示耗时，禁止重复提交，替换上次结果；不自动写锚点或移动旧音符。

## 发现并修复的问题

1. **导入的 BPM 字段不一致。** MC 参考点为 144，`tempo.bpm` 却保留音频估计 143.555；添加锚点时会用错默认值。新导入同步首点，继续保持导入参考未确认，冲突的多谱参考不会被任意选定。
2. **段落计划丢失单值参考。** 历史音频导入只有 `tempo.bpm`，局部证据以前显示没有参考。现在保留为未确认音频参考；不伪造锚点或提高信任。
3. **已确认多 BPM 段落的计算不准确。** 跨锚点时只用段首 BPM 计算拍数和加权；现在按覆盖时长积分，晚起的已确认锚点也不能确认此前区间。
4. **融合设置被旧计划覆盖。** 请求中的 rate/chord/gap/peak/hold 没有真正替换旧预算。现在从冻结的音乐证据派生新融合计划，实际使用新参数，保留父计划和两份原谱，不重新分离或推理，不自动采用。
5. **重复全曲分析造成提交等待。** 修复前一次生成提交约 23 秒，重复分析实测约 25 秒。分析与生成共用经过内容校验的精确计划缓存；修复后重复请求约 0.25–0.44 秒。首次新分析仍需计算，更改相关设置、BPM 参考或计划版本会失效。
6. **部分失败显示为全成功。** 已完成但存在 `advanced_errors` 的任务显示「部分完成」，列出失败声部/组合，并保留已完成候选。
7. **旧曲包导入丢失音源身份。** 保存已知音乐来源与导入字节信息；仅明确一致的音乐 URL 能继承，封面不能冒充音源。
8. **MCZ 误用包内第一个音频。** 原实现可能把 keysound 当歌曲，导入错误长度并裁空谱面。现在按各 MC 的 BGM 相对引用选择唯一歌曲；缺失、多个目标、重复对象、绝对或越界引用拒绝导入。真实上传端点已验证 keysound-first 夹具：正确导入 2 秒歌曲与 1.5 秒音符；缺 BGM 返回 400。

另用已有「私は雨」普通任务调用真实 `from-source(type=job)` 接口：完整 230.080 秒、导入参考 144 BPM、单值与首点一致、保持待确认；YouTube 音乐身份正确继承，并明确当前输入是已编码的曲包音频。

## 额外接口边界

- 无效声部、重叠/越界片段、无效组合、过期项目版本被拒绝，既有项目与队列不变。
- 融合预算分别设为 0.5 与 30 音符/秒，候选分别为 **123 / 1536** 个音符，实际预算不同；无新 GPU 任务，采用版本不变。这两个极端值是参数作用测试，不是推荐设置。
- 人声与伴奏版本的默认试听分别对应正确源文件；音频采样与峰值安全增益匹配，最大误差 0。HTTP Range 拖动定位返回正确字节区间。
- 拆分为 0–37、37–197、197–230.080 秒后，跳过中间段的成品为 **70.080 秒 / 3,090,528 帧**。音符和音频使用相同采样映射，完成后恢复三个片段均纳入。
- 缓存校验覆盖旧版、不同源、不同长度、参数/参考变化、损坏内容、融合派生计划和并发重复请求。采样种子/温度改变可复用节奏证据，但实际模型缓存仍按采样设置区分。
